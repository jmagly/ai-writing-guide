# AIWG CI Pin Manifest
#
# Tracks the immutable digests and commit SHAs that the CI workflows pin
# against, plus the rationale and the intentional-update process. The
# goal: workflow runs are reproducible across time, and any digest/SHA
# repointing is a reviewable change rather than a silent supply-chain
# attack surface.
#
# Source rules:
#   .claude/rules/dev-idempotent-builds.md  (rule 2: no :latest, rule 4: lock files)
#   .claude/rules/dev-pipeline-safety.md
#
# Originating change: #1281 (A3 — digest-pin containers) + #1282 (A4 —
# SHA-pin actions), Wave 2 of supply-chain hardening epic #1278.
#
# Format: one row per pinned reference.
#   <kind>  <name>            <pin>                             <resolved-version>   <date-pinned>   <update-rationale>
# Use this as the source of truth when reading workflow diffs — a digest
# change here without a corresponding "Bump pin" entry below is a red flag.
#

# Notes on action pinning:
# - Pin is the 40-character commit SHA of the *immutable* patch tag (v4.X.Y),
#   resolved at pin time via `git ls-remote https://github.com/actions/<repo>
#   refs/tags/v4`. The trailing comment in each workflow line shows the
#   semantic version so readers see at a glance what the SHA refers to.
# - actions/checkout: v4 (floating) currently aliases the v4.3.1 immutable
#   patch tag. v4.3.0 release date 2025-08-11; v4.3.1 followed.
# - actions/upload-artifact: v4.6.2 release date 2025-03-19.
# - actions/setup-node: v4.4.0 used by .github/workflows/npm-publish.yml.
# - sigstore/cosign-installer: v3.10.1 is the last release of the v3 line.
#   The v3 line installs Cosign v2.x; the cosign-installer v4 line is
#   required if/when we move to Cosign v3.x. AIWG pins to Cosign v2.x for
#   stability — the keyless-signing API (`cosign sign-blob` with
#   `--bundle`) is identical across v2.x and v3.x, so the operator-side
#   upgrade path is just a digest+version bump in this file plus a one-line
#   workflow change once the v4 installer matures.
#

# ============================================================================
# Update process
# ============================================================================
#
# 1. Open an issue describing why the bump is wanted (CVE in pinned version,
#    needed new feature, etc.). Link any upstream advisory.
# 2. Resolve the new pin:
#    - Container digest:   `docker pull <name>:<tag>` then take the
#                          `Digest: sha256:...` line from the pull output.
#                          Alternatively: `docker buildx imagetools inspect
#                          <name>:<tag>` for multi-arch awareness.
#    - Action SHA:         `git ls-remote https://github.com/actions/<repo>
#                          refs/tags/<semver-tag>`
# 3. Update *all* workflow occurrences in a single commit. Audit with:
#    `grep -rn "<pinned-thing>" .gitea/workflows/`
# 4. Append a row to this file under the same `<kind>` section. Format the
#    `<update-rationale>` column as: short description + issue ref
#    (e.g., "CVE-2026-12345 fix, #1310").
# 5. Commit message format:
#    `chore(ci): bump <name> pin to <version> (refs #<issue>)`
# 6. Verify a full CI run passes on the bump commit before tagging anything
#    that depends on it.
#
# Cadence: pins are not bumped on a fixed schedule. A bump is triggered by
# (a) a security advisory against the current pin, (b) a needed feature in
# a newer release, or (c) an explicit audit decision to roll forward. See
# also #1310-class follow-ups for any Dependabot-equivalent automation on
# Gitea Actions.
